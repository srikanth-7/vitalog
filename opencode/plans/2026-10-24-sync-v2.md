# Sync v2 — pull + push of reports, profiles and account settings

*Requested 2026-10-24 (product owner). Aligns with docs/SHARING.md (build order
2 + 3) and docs/PENDING_TASKS.md #10–#12. Replaces plaintext Sync v1; the
v1 `reports` / `lab_results` tables are dropped when v2 ships.*

## What the owner asked for

Once signed in, the Sync tap should move — both ways —
1. the current reports (records),
2. **account settings** (Display settings etc.),
3. **family member profiles** the user added (identity data; not "the records"
   — records live inside the sealed `reports` blobs anyway),
4. **pull before push**, so a push by any linked device/family member is not
   lost, then push our own state (pull → merge → push).

## Scope: what syncs and what never syncs

**Syncs** (all sealed server-side):
- Profiles: name, sex, birth year; per-account relation + "this is me".
- Reports + their results (inside the sealed report blob; results never leak
  as separate columns).
- Account state (one sealed blob): `themeMode`, `accent`, `simpleMode`,
  hidden Home sections, `category_choices.json` learnings, `stateVersion`,
  `updatedAt` (inside the blob; drives LWW).

**Never syncs** (phone-only, by decision):
- Original documents / OCR text (never leave the device — standing decision).
- Keychain/Keystore cipher keys, session tokens, the account **private** key
  and recovery key (recovery keys are exported manually, only with consent).
- `reviewed`, `edited`, usual-range judgments — re-judged locally after merge.
- `onboarded` (per-install UX; onboarding always runs on a fresh install).
- Language setting (timed with task #14 — more languages).

## Server additions (beyond SHARING.md schema)

```sql
-- one row per account; sealed display/settings/learnings
create table account_state (
  user_id uuid primary key references auth.users on delete cascade,
  wrapped_key bytea not null,     -- batch/settings key, X25519-wrapped to the account key pair
  sealed bytea not null,          -- settings + category_choices + {stateVersion, updatedAt}
  updated_at timestamptz not null default now()
);
-- profiles: add tombstone column for cross-device member deletes
alter table profiles add column deleted boolean not null default false;
```

RLS mirrors `profile_access` visibility; `account_state` is owner-only
(`auth.uid() = user_id`). A later phase adds an RPC set for batched pull
(one round-trip) rather than 4 selects; fine to start with plain selects.

## Merge rules (pull → merge → push)

1. **Order** on the Sync tap: `ensureAccountKeys()` → pull → merge → push
   tombstones → push live rows → re-judge usual ranges locally → notice.
   Pull runs in one round-trip; every unsealable row wins its place; rows that fail to unseal (key rotated, revoked) are skipped and counted in
   the sync notice, never guessed at.
2. **LWW** per entity on `updated_at` (server) / `updatedAt` or report
   metadata (sealed inside the blob). Ties → keep the local row; both survive
   if ids differ (duplicate combine remains the owner-initiated flow from
   SHARING.md).
3. **Deletes**: report deletes push `deleted = true` tombstones; pull applies
   them (removes local, adds to a tombstone cache so a slow pusher can't
   resurrect). Profile deletes happen only via leave/remove (+ rotation).
   Settings: no delete semantics; stale blobs lose the LWW compare.
4. **Member ids stay stable**: device-generated ids are the identity for
   reports/results/profiles; merge never re-ids.
5. Lock merge on the repository lock (same pattern as processReport).

## Build order

**Phase 1 — contracts first (tests before code, repo style)**
- `test/privacy/sync_v2_test.dart`: seal/push/pull/merge/tombstone round-trip
  with in-memory fakes; multi-device LWW case; "can only pull what we can
  unseal"; settings blob version merge; tombstone non-resurrection.
- Extend `sharing_crypto_test.dart` for the account batch-key wrap/unseal.

**Phase 2 — account key pair + recovery (SHARING.md build order 2)**
- First sign-in: generate X25519 pair; private → secure storage (reuse
  `SecureSessionStorage` tier); public → `account_keys` table.
- Recovery key export/import (print / paste), shown once when Sync turns on.
- One offer per account, cancellable; never silently skip.

**Phase 3 — Sync v2 engine**
- `SyncV2Service` in `data/sharing/`: seal/push/pull/merge/tombstones for
  profiles, reports (+results), `account_state`.
- Repository: `syncFamilyState()` replaces `syncReports`; merge under lock;
  usual-range re-judge; duplicate detection per member unaffected.
- `HealthBloc`: notices for pulled-changes count ("3 updates came in"),
  unsealable-skip count, conflicts; preserve `RefreshHealthData` no-flash rule.
- `SettingsCubit`: serialize state into the sealed blob with `stateVersion`;
  apply pulled settings only if version > local.

**Phase 4 — UI + cleanup**
- Sync button unchanged; new optional readout line after sync.
- Recovery key prompt/export screen (once).
- Supabase: new tables via `supabase/schema_v2.sql`; **drop plaintext v1
  tables in this step** (nothing real has synced yet — safe per owner).
- Update `SUPABASE_REQUIREMENTS.md`/`GO_LIVE.md`; record the 2026-10-22
  "names stay on the phone" note as superseded-for-synced-profiles.
